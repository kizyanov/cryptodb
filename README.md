# cryptodb

Репозиторий базы данных **PostgreSQL** проекта *cryptodb*, которая поднимается
в **Docker** и настроена под маломощный хост.

> **Ограничения целевой машины:** 1 ядро CPU · 1 ГБ RAM · 10 ГБ диска.

> **Статус:** Docker-окружение PostgreSQL с тюнингом под слабый хост.
> Миграции и схема БД ведутся **в отдельном репозитории**; прикладного кода здесь нет.

## Структура репозитория

```
cryptodb/
├── docker-compose.yml     # подъём PostgreSQL в Docker (с ограничениями ресурсов)
├── .editorconfig          # единые настройки редактора
├── .env.example           # шаблон переменных окружения
├── .gitignore
├── README.md
├── scripts/
│   ├── backup-push.sh     # выгрузка снимка БД на домашнюю машину (по расписанию)
│   └── restore-remote.sh  # восстановление дампа на домашней БД (вызывается по ssh)
└── db/
    ├── init/              # SQL-скрипты, выполняемые при ПЕРВОМ создании тома данных
    └── postgresql.conf    # тюнинг PostgreSQL под 1 ядро / 1 ГБ RAM
```

## Быстрый старт (Docker)

Требуется Docker с compose-плагином (обычно `docker compose`).

```bash
# 1. Создать окружение и задать надёжный пароль
cp .env.example .env
#    отредактируйте .env: PGPASSWORD=<надёжный пароль> (openssl rand -hex 16)

# 2. Поднять базу (первый запуск скачает лёгкий образ postgres:*-alpine)
docker compose up -d

# 3. Проверить состояние
docker compose ps            # STATUS должен стать healthy

# 4. Подключиться (psql уже есть внутри контейнера)
docker compose exec db psql -U cryptodb -d cryptodb

# логи сервера
docker compose logs -f db    # выход — Ctrl+C
```

Сервер слушает **все интерфейсы** (`0.0.0.0:5432`) — к нему могут подключаться
и другие машины в сети (например, соседние через WireGuard). **Безопасность:**
эта БД не должна быть доступна из интернета — если у хоста есть публичный IP,
обязательно ограничьте доступ фаерволом (разрешите порт только для нужных
подсетей/IP) и задайте надёжный `PGPASSWORD`. Вариант «только локально» —
верните в `docker-compose.yml` строку `"127.0.0.1:${PGPORT:-5432}:5432"`.

### Остановка и данные

```bash
docker compose down     # остановить; данные сохраняются в томе cryptodb_pgdata
docker compose up -d    # поднять снова — данные на месте

docker compose down -v  # остановить И удалить ВСЕ данные (необратимо!)
```

Данные лежат в именованном томе `cryptodb_pgdata` и не зависят от контейнера,
так что репозиторий можно свободно обновлять (`git pull` + `docker compose up -d`).

## Что настроено под ограничения машины

| Ограничение | Как учтено |
|---|---|
| 1 ГБ RAM | PostgreSQL-параметры под малый объём (`shared_buffers=128MB`, `max_connections=50`, `work_mem=4MB`…); контейнеру выделено не более 512 МБ (`mem_limit: 512m`) — остальное ОС и Docker |
| 1 ядро CPU | `cpus: 1.0`; `autovacuum_max_workers=2`; редкие чекпоинты (`checkpoint_timeout=15min`) — меньше фоновой работы |
| 10 ГБ диск | лёгкий образ `postgres:18-alpine`; ротация логов Docker (10 МБ × 3); ограниченный WAL (`max_wal_size=256MB`); данные — только в одном томе |

Полный список параметров — в [`db/postgresql.conf`](db/postgresql.conf) с пояснениями.

> Если контейнер убивается по памяти (в логах `docker compose logs db` ищете `OOM`),
> уменьшите в `db/postgresql.conf` `shared_buffers` до 96 МБ и выполните
> `docker compose up -d --force-recreate db`.

## PostgreSQL без Docker

Если Docker на машине недоступен, базу можно поднять вручную с тем же тюнингом:

```bash
cp .env.example .env
initdb -D ./pgdata -U "$PGUSER"          # один раз
pg_ctl -D ./pgdata -o "-p $PGPORT -c config_file=$PWD/db/postgresql.conf" start
psql -h "$PGHOST" -p "$PGPORT" -U "$PGUSER" -d "$PGDATABASE"
```

## Синхронизация с домашней копией (по расписанию)

Схема: основная машина по расписанию (cron) делает **полный снимок БД**
(`pg_dump`, без остановки сервера) и по **ssh выгружает его на домашнюю
машину**, где дамп сразу восстанавливается в домашнюю БД для чтения/аналитики.

Такая схема выбрана под ваши условия:

- основная база не принимает соединений из интернета (WireGuard) — исходящий
  ssh инициирует сама основная машина, открывать порты наружу не нужно;
- домашняя машина может быть недоступна до недели: неудачные запуски просто
  завершаются ошибкой, а следующий запуск делает свежий дамп — пропущенные дни
  нагоняются автоматически, т.к. снимок всегда полный и текущий;
- временный дамп на основной машине удаляется после выгрузки (диск 10 ГБ не забивается).

### Как это устроено

```
основная машина (cron, ежедневно)
  scripts/backup-push.sh
    1) docker compose exec db pg_dump …        → временный .sql (полный снимок)
    2) rsync по ssh                             → дом: backup/cryptodb-latest.sql
    3) ssh: scripts/restore-remote.sh           → домашняя БД: таблицы заменяются
```

### Предпосылки

1. Основная машина может установить **исходящее** ssh-соединение с домом
   (ключ без пароля):

   ```bash
   ssh-keygen -t ed25519            # если ключа ещё нет
   ssh-copy-id user@home.example.com
   ssh user@home.example.com echo ok
   ```

2. На домашней машине поднят этот же репозиторий (`docker compose up -d`),
   пользователь может выполнять `docker compose` (группа `docker`), каталог для
   дампа создан:

   ```bash
   ssh user@home.example.com 'mkdir -p /srv/cryptodb/backup'
   ```

3. sshd на доме доступен из интернета (по вашим условиям — да); при доме за NAT
   проброшен порт ssh.

### Настройка и запуск

Переменные `BACKUP_*` — в `.env` (см. `.env.example`). Ручной запуск:

```bash
./scripts/backup-push.sh
```

Расписание (cron **основной** машины, пример — ежедневно в 03:17):

```
17 3 * * * cd /путь/к/cryptodb && ./scripts/backup-push.sh >> /var/log/cryptodb-backup.log 2>&1
```

Восстановление вручную на доме (если потребуется):

```bash
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U cryptodb -d cryptodb \
  < /srv/cryptodb/backup/cryptodb-latest.sql
```

### Ограничения и заметки

- Каждая выгрузка передаёт **весь объём БД** (rsync со сжатием): с ростом базы
  растёт и трафик. Когда это станет тяжело — перейдём на инкрементальные бэкапы
  (pgBackRest) или логическую репликацию.
- Домашняя копия — **для чтения**: восстановление перезаписывает таблицы
  целиком, изменения, сделанные на доме, не сохранятся.
- Безопасность: даже на доме не пробрасывайте порт БД 5432 в интернет — для
  доступа извне используйте ssh-туннель; дампы содержат данные, поэтому
  защищайте и каталог `BACKUP_HOME_DIR` на доме.

## Схема и миграции

Миграции и описание схемы БД ведутся **в отдельном репозитории** — здесь их нет:
этот репозиторий отвечает только за запуск PostgreSQL в Docker.
Первоначальное наполнение при первом старте (расширения, стартовые данные)
делается через [`db/init`](db/init/README.md).

## Переменные окружения

Параметры описаны в [`.env.example`](.env.example). Файл `.env` (с реальными
значениями) в git **не** коммитится.
